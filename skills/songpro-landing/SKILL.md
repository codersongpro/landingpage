# 송프로 랜딩페이지 제작

송프로가 만든 앱이나 기획한 행사를 한 페이지로 소개한다. 페이지 디자인은 정해진 틀 하나로 찍어내지 않는다. 소개하는 대상, 보는 사람, 실제 앱 화면을 보고 가장 어울리는 디자인을 매번 새로 정한다. 예시는 참고만 하고 그대로 따르지 않는다.

## 폰트 원칙

폰트도 디자인처럼 프로젝트마다 고른다. 따로 고를 이유가 없으면 Pretendard Variable로 시작하지만, 본문과 제목 모두 더 어울리는 폰트가 있으면 그걸 쓴다. 예를 들어 손글씨 느낌의 학생 행사면 본문까지 둥근 고딕으로, 공식 연수면 제목을 명조로 바꿀 수 있다.

- 고르는 기준: 한글 글자 수(완성형 2,350자 이상 또는 KS X 1001 전체)가 충분하고, 본문으로 쓸 폰트는 작은 크기에서도 잘 읽혀야 한다. 폰트는 한두 가지, 많아야 세 가지.
- 고르는 곳: Google Fonts, 눈누(noonnu.cc), 각 폰트 공식 배포처. SIL OFL처럼 웹폰트 사용과 상업적 이용이 허용된 폰트만 쓴다. 라이선스를 확인하고 페이지 소스 주석에 폰트 이름·출처·라이선스를 적는다.
- 내려받는 방법: 간단한 페이지는 CDN(jsDelivr, Google Fonts) 링크로 불러온다. 자기 도메인에 배포하거나 오프라인에서도 열려야 하면 woff2 파일을 내려받아 `fonts/` 폴더에 두고 `@font-face`로 연결한다. 한글 폰트는 서브셋(dynamic subset)이나 woff2만 써서 용량을 줄인다.
- 대체 순서: font-family 끝에는 시스템 한글 폰트를 붙인다. 예: `"고른폰트", "Pretendard Variable", Pretendard, -apple-system, BlinkMacSystemFont, "Apple SD Gothic Neo", "Malgun Gothic", sans-serif`
- `font-display: swap`으로 폰트가 늦게 와도 글자가 먼저 보이게 한다.

분위기별 폰트 예 (참고용, 프로젝트에 더 맞는 폰트가 있으면 그걸 쓴다)

| 분위기 | 제목 | 본문·숫자·라벨 |
|---|---|---|
| 깔끔한 실무 도구 | Pretendard Variable, Wanted Sans, 영문은 Inter | Pretendard Variable, SUIT, 숫자는 Inter (tabular-nums) |
| 차분한 업무 앱 | SUIT, Gmarket Sans Bold, 영문은 Manrope | IBM Plex Sans KR, Noto Sans KR, SUIT |
| 개발·기술 | 영문 Space Grotesk, 한글 Galmuri(픽셀) | Pretendard Variable 또는 IBM Plex Sans KR, 코드는 JetBrains Mono·D2Coding |
| 학생·축제 | Jalnan(잘난체), Black Han Sans, Ownglyph 계열 | NanumSquare Round, Gowun Dodum 같은 둥근 고딕 |
| 연수·공식 행사 | Noto Serif KR, 마루부리, 리디바탕 | Noto Sans KR, IBM Plex Sans KR |

함께 쓰는 자료 (이 스킬 폴더 안에 들어 있어 따로 설치할 필요 없음)
- `references/humanize-korean.md`: 문구를 다 쓴 뒤 읽고 A~J 패턴을 걷어낸다. 내용·수치·고유명사는 건드리지 않는다.
- `references/frontend-design.md`: 레이아웃·타이포를 정할 때 읽는다. 크림 배경+세리프 제목+테라코타 포인트 조합은 쓰지 않는다.
- `references/design-examples.md`: 실제로 써 본 디자인 방향 예시 세 가지(클린 블루, 웜 스톤, 터미널 네온)의 색 변수와 섹션 흐름. 참고용이다.
- `references/theme-factory.md`, `references/themes/`, `references/theme-showcase.pdf`: 색 조합 아이디어를 얻을 때 본다. 폰트는 가져오지 않는다(서버용 영문 폰트라 한글 웹에 맞지 않음).
- `references/security-check.md`: 신청 폼, 외부 API, 개인정보가 얽히면 읽고 점검한다.
- `references/licenses/`: 포함된 자료의 출처와 라이선스.

같은 이름의 스킬이 따로 설치돼 있어도 이 폴더의 파일을 기준으로 한다.

## 1. 인터뷰

이미 받은 정보는 다시 묻지 않는다. 비어 있는 것 중 결과를 크게 바꾸는 것만 최대 5개, 선택지와 함께 묻는다.

1. 무엇을 소개하나: 앱·도구 / 연수·워크숍 / 행사·대회 / 공모전 출품작 / 개인·팀 소개
2. 누가 보나: 교사 / 공무원·교직원 / 학생 / 학부모 / 개발자·일반인
3. 보고 나서 무엇을 하게 할까(CTA): 앱 열기 / 다운로드 / 신청 / 문의 (링크 주소 포함)
4. 참고 자료: 앱 URL, 기획서, PRD, 행사 계획서, 포스터, 스크린샷
5. 원하는 느낌이 있나: 맡기기 / 참고 사이트 URL / 키워드(예: 따뜻한, 미니멀, 레트로)

앱 URL을 받으면 브라우저로 열어 기능, 화면, 단축키, 사용 순서를 직접 확인한다. 기능을 추측으로 지어내지 않는다.

## 2. 디자인 고르기

테마를 미리 정해 두지 않는다. 아래 순서로 이 프로젝트에 가장 어울리는 디자인을 에이전트가 직접 정한다.

1. 재료 모으기
   - 소개할 앱이 있으면 브라우저로 열어 실제 배경색·글자색·강조색·모서리·그림자·폰트를 뽑는다(`getComputedStyle`, `:root` CSS 변수). 랜딩은 앱을 열었을 때와 같은 느낌으로 이어져야 한다.
   - 포스터, 로고, 키비주얼, 기관 색이 있으면 그 주조색을 출발점으로 삼는다.
   - 사용자가 참고 사이트나 키워드를 줬으면 그것이 가장 우선이다.
2. 성격 읽기: 누가 보는지(교사·학생·학부모·공무원·개발자), 어떤 자리에서 보는지(교실 TV, 업무 PC, 휴대폰), 어떤 기분이어야 하는지(믿음직함, 신남, 차분함, 전문성)를 한 줄로 적는다.
3. 방향 후보 2~3개 떠올리기: 각각 색 팔레트, 폰트 조합, 레이아웃 밀도, 움직임을 짧게 정한다. `references/frontend-design.md`, `references/design-examples.md`, `references/themes/`를 아이디어로만 쓴다.
4. 하나 고르기: 2번의 성격에 가장 잘 맞고 앱 화면과 이어지는 안을 고른다. 사용자에게는 고른 방향과 이유를 한두 줄로 알리고 바로 만든다. 사용자가 고르고 싶다고 했을 때만 후보를 보여 준다.
5. 디자인 토큰으로 정리: `:root`에 색·모서리·그림자·여백·폰트 변수를 먼저 정하고 그 변수로만 스타일을 쓴다.

지킬 것
- 매번 같은 파란 버튼, 같은 카드 그리드로 흐르지 않는다. 직전에 만든 랜딩과 비슷해지면 다시 고른다.
- 강조색은 하나, 많아야 보조 하나. 강조색 위 글자 대비가 WCAG AA(4.5:1)를 넘는지 확인한다.
- 크림 배경+세리프 제목+테라코타 포인트, 보라 그라데이션+유리 카드처럼 AI가 자주 내는 조합은 피한다.
- 섹션 구성은 자료에 맞춰 정한다. 앱이면 히어로→쓰는 장면→기능→사용법→시작하기→FAQ→CTA, 행사면 히어로(일시·장소·대상)→취지→프로그램→강사→신청→오시는 길→FAQ가 출발점이지만 빼고 더하는 것은 자유다.

## 3. 문구 먼저

디자인보다 문구를 먼저 완성한다. 섹션별 제목·설명·버튼 문구를 표로 보여 주고 확인을 받은 뒤 코드로 넘어간다(사용자가 바로 만들라고 하면 생략).

- 제목은 사용자가 얻는 장면으로 쓴다. 예: "확대하고 짚고 쓰고 녹화까지 한 번에", "공문 정리부터 학생 기록까지 앱 하나로"
- 숫자·고유명사·단축키처럼 구체적인 걸 넣는다. 예: "F7 · F8 · F9 · F10, 네 개면 충분합니다"
- 고른 디자인에 말투를 맞춘다. 깔끔한 도구는 짧고 쉬운 말, 업무 앱은 차분한 설명, 개발·기술 쪽은 1인칭과 코드 표기를 섞는 식
- 제목 두 줄, 설명 두 문장 이내
- "혁신적인", "스마트한", "새로운 경험", "여정", "생태계"는 쓰지 않는다
- 다 쓴 뒤 `references/humanize-korean.md` 기준으로 한 번 더 검사한다

자료에 없는 섹션은 빼고, 빈칸을 지어서 채우지 않는다.

## 4. 만들기

- HTML 파일 하나에 CSS·JS를 모두 넣는다. 외부 리소스는 폰트만(CDN 링크 또는 함께 넘기는 `fonts/` 폴더)
  - Pretendard Variable을 쓸 때: https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/variable/pretendardvariable-dynamic-subset.min.css
  - 다른 폰트는 위 폰트 원칙대로 고르고 불러온다
- 공통: `word-break:keep-all`, 제목에 `text-wrap:balance`, 본문 줄 길이 640px 이내, 본문 16~18px·줄 간격 1.6~1.7
- `<head>`에 title, description, og:title, og:description, og:image, theme-color(페이지 --bg), viewport
- 이미지가 없으면 앱 화면을 HTML/CSS로 단순하게 그린 목업. 실제 스크린샷을 받으면 그것을 씀
- 아이콘은 인라인 SVG. 이모지 헤더는 쓰지 않는다
- 메뉴는 모바일에서 햄버거로 접고, 터치·마우스 모두 동작
- 애니메이션은 고른 디자인에 맞게(살짝 떠오름, 스크롤 데모, 타이핑·글로우 등). 넣지 않는 것도 선택지다. `prefers-reduced-motion`이면 끈다
- 소리가 나는 요소는 기본 꺼짐, 켜기 토글을 둔다
- 버튼·링크에 focus 스타일

보안·개인정보
- 페이지 안에서 신청 정보를 저장하지 않는다. 신청은 구글폼 같은 외부 링크로
- API 키, 개인 휴대폰 번호는 넣지 않는다. 문의는 공식 메일이나 폼으로
- 학생 사진·이름은 사용자가 공개 동의를 확인했다고 할 때만

제작자 표기는 사용자가 넣어 달라고 할 때만 푸터나 '만든 사람' 섹션에 넣는다.

```
송동석 (Songpro / Dustin)
AI Product Builder · Educator · Data Analyst
즐거움은 더하고, 불편함은 덜고.
© 2026 Songpro. All rights reserved. 이 페이지의 내용과 디자인을 허락 없이 복제·재배포할 수 없습니다.
```

## 5. 확인

완성 전에 브라우저에서 직접 열어 본다.

먼저 자동 점검을 돌린다(Node.js 18+와 Playwright가 있을 때). 스크린샷 3장, 가로 스크롤·넘침, 폰트 로딩, 글자 대비, 빈 링크, `<head>` 메타태그를 한 번에 확인한다. `✗`로 나온 항목을 고친 뒤 다시 돌리고, 스크린샷은 직접 눈으로 본다.

```
node <이 스킬 폴더>/scripts/check_page.js index.html --out check-result --links
```

Playwright가 없으면 `npm i -D playwright && npx playwright install chromium`으로 설치하거나, 아래 항목을 브라우저에서 손으로 확인한다.
- 375px, 768px, 1280px 세 폭에서 스크린샷: 가로 스크롤, 글자 넘침, 버튼 줄바꿈
- 고른 폰트가 실제로 불러와졌는지(`document.fonts` 확인), 한글 글자가 대체 폰트로 깨져 보이지 않는지
- 어두운 디자인이면 대비, 밝은 디자인이면 연한 글자(--text-3, --text-4)가 너무 흐리지 않은지
- 소개하는 앱과 나란히 띄워 색과 느낌이 이어지는지
- 모든 CTA 링크가 실제 주소로 가는지
- 문구를 `references/humanize-korean.md` 기준으로 마지막 점검

## 6. 전달

- 기본: 아티팩트로 게시해서 바로 링크를 공유할 수 있게 한다
- 자기 도메인에 올린다고 하면 index.html 파일로 준다. 폰트를 내려받아 썼으면 `fonts/` 폴더까지 zip으로 묶는다. Vercel 배포를 원하면 그 순서까지 안내한다
- 수정 요청이 오면 해당 섹션만 고친다. 전체를 다시 쓰지 않는다
- 사용자가 결과 디자인이 마음에 든다고 하면 `references/design-examples.md`에 예시로 추가하자고 제안한다
